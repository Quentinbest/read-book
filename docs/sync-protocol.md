# Sync protocol (byte level)

Status: a draft for its security review (Codex and the owner), written 2026-10-17 for Stage 1 of `docs/sync-plan.md` (#92). Nothing in it is built. Stage 1's code (1a, 1b, 1c) starts only after the owner has reviewed it. Values marked (prov.) are provisional, as in the plan. Two questions it raises wait for the owner: items 113 (#86) and 114 in `docs/pending-approvals.md`.

This file says how SY1–SY34 are put into bytes: every file in the `Linen` folder, what is signed and how, how a device joins, leaves and is trusted, and what may be removed when. It adds no behaviour of its own except where it says so (§10). Its rules are SP1–SP37; code cites them beside the plan's (`// SP15, SY11: …`). Where this file and the plan disagree, the plan wins until the owner approves a change.

## 1. Primitives and encodings

| ID | Rule |
|---|---|
| SP1 | **Identifiers.** A library ID and a writer token are each 16 random bytes from the OS's CSPRNG; a device ID is the first 16 bytes of `H("linen-sync/device-id/v1" ‖ its Ed25519 public key)`, so an ID names exactly one key (a new ID, SY7, comes with a new key); each is written as 32 lowercase hex digits. A book's sync ID is a version-4 UUID, lowercase with hyphens. A record key is UTF-8, at most 256 bytes, in the forms SY9 lists, plus `choice:` (SP12). A version is named by its *version ID*, `{ "d": device, "s": sequence, "h": version hash }` (SP11). Sequences and counters are integers from 1 up to 2^53 − 1. |
| SP2 | **Names in storage are lowercase.** Both storages fold case, and Google Drive folds Unicode normalisation (`docs/spikes/sync-folders.md`), so two names that differ only in case would be one file. Every name Linen writes uses only `[a-z0-9.-]`, a subset of SY2's set; hashes and IDs are lowercase hex. A listed name with an upper-case letter, a space or anything else is a conflict copy or a stranger's file (SP7). |
| SP3 | **JSON.** Every file but a book and a body is UTF-8 JSON (RFC 8259), with no byte-order mark. A parser refuses duplicate keys, nesting deeper than 32, a number that isn't an integer within ±(2^53 − 1), and a string with an unpaired surrogate; sizes are checked before reading and while reading (SY28). Unknown fields are kept wherever the plan says they are kept (SY9) and are covered by every hash and signature, since those are over bytes (SP5, SP6) or over the canonical form (SP11). Bytes inside JSON (keys, signatures, nonces, ciphertext) are base64url without padding; hashes inside JSON are lowercase hex. |
| SP4 | **Cryptography.** One suite, named by the envelope's `"sync": 1`; a new suite is a new number, never a negotiation. |

SP4's suite:

| Use | Primitive |
|---|---|
| Hash `H` | SHA-256 |
| Signatures | Ed25519 (RFC 8032), verified strictly: canonical `S`, and public keys of small order refused (`ed25519-dalek`'s `verify_strict`) |
| Keyed names (SY3) | HMAC-SHA256 under the naming key |
| Key derivation | HKDF-SHA256 |
| Sealing | XChaCha20-Poly1305 with a random 24-byte nonce |
| Key agreement (enrollment) | X25519 |
| The recovery code (SY34) | Argon2id, m = 64 MiB, t = 3, p = 1, 32-byte output (prov.) |
| Fingerprint shown to the reader | the first 10 bytes of `H("linen-sync/fpr/v1" ‖ public key)`, as 4 groups of 4 Crockford base32 characters |

Every hash, HMAC, HKDF and signature input starts with its own domain string (`linen-sync/…/v1`), so no value made for one purpose can be passed off as another.

**Exact inputs.** `‖` joins fixed-length binary fields: IDs are 16 bytes, hashes, keys and `root` 32, nonces as stated, sequences 8 bytes big-endian; a domain string or any other variable-length field is preceded by its length as 4 bytes big-endian. HKDF is RFC 5869's Extract then Expand with SHA-256, the salt stated (zero-length when none is), the `info` string as given and 32 bytes of output. Argon2id is RFC 9106's version 0x13, with m in KiB (65,536), t, p and the salt as given and no secret or associated data. X25519 is RFC 7748's, and an all-zero shared secret is refused. XChaCha20-Poly1305's associated data is the bytes stated, joined the same way. Stage 1c's PR adds test vectors for every derivation, seal and signature here, and code is checked against them.

### 1.1 Signed files

| ID | Rule |
|---|---|
| SP5 | **The envelope.** A signed file is `{ "sync": 1, "type": T, "payload": B, "sigs": [ { "by": S, "sig": G } … ] }`. `B` is the payload's exact bytes in base64url, so nothing is ever re-encoded before it is checked. The *payload hash* is `H(payload bytes)`, and a file is named, chained and attested by it, never by its envelope, so a signature's encoding can't change a file's identity. The payload is itself JSON and repeats `type` and `library`. A single writer's file (`change`, `device`, `view`, `claim`, and the enrollment exchange, SP24) also repeats its writer's `device` and `writer` token. Membership records and escrows (SP19) carry neither: their fields are as SP19's table gives them, their signers are named in `sigs` (`by`), and which signers each type needs is SP19's and SP20's rule; a payload whose `type` or `library` differs from what the reader expected is refused before its signature is checked. |
| SP6 | **What is signed.** Each signature is over `"linen-sync/sig/v1" ‖ 0x00 ‖ T ‖ 0x00 ‖ library ID (16 bytes) ‖ signer (16 bytes; zero for a code key) ‖ seq (8 bytes, big-endian; 0 when the type has none) ‖ prev (32 bytes: a change file's `prev`, zeros for its first and for every other type) ‖ vroot (32 bytes: for a change file, `H("linen-sync/vlist/v1" ‖ its version list)`, the 48 bytes per version that a spine keeps as `v`, in the file's order; zeros for every other type) ‖ payload hash (32 bytes)`. Signing `prev` and `vroot` lets a change's link to its predecessor, and the versions it held, be checked from its signature alone after the file is gone, as spines and fork proofs need (SP17, SP30); a spine entry whose `v` doesn't give the signed `vroot` is refused. `seq` is a change file's sequence, a view's generation or a device file's counter, so a signature names its place in the signer's history and two signatures for one place prove equivocation without the files (SP30). The library ID stops a file signed for one library from counting in another (SY29). `by` is a device ID, or `"code"` for the recovery code's key (SP22). |

## 2. The folder

| ID | Rule |
|---|---|
| SP7 | **Writing and reading files.** A write goes to `.linen-tmp-‹16 hex›` beside its target and is renamed onto it (SY2). A half-synced file fails its hash or signature and is skipped and read again on a later pass (SY11). A name the storage made (a conflict copy, SY2's opaque token) is read only as a candidate for the file it copies: for a single-writer file it is checked as that writer's, merged by the owner and removed; for a shared object, SY11's hash rule decides. Nothing outside the layout in SP8 is read, and nothing in it is read before its size fits SP8's limit. |

Only `trust/`, `enroll/`, `blobs/` and `books/` have more than one writer, and every file in them is fixed by its name (content-addressed) or by its signer, so two writers never write one name with different bytes (SY11). Every file in `enroll/` is written once and never rewritten (SP24).

| ID | Rule |
|---|---|
| SP9 | **Keyed names.** The naming key is 32 random bytes made at the library's first setup and never changed (SY3; item 108: the folder isn't encrypted, so a removed device that knows the key learns nothing it couldn't read). A body's name is `hex(HMAC(naming key, "linen-sync/blob/v1" ‖ H(body)))`, a book's `hex(HMAC(naming key, "linen-sync/book/v1" ‖ H(file)))`: 64 hex digits, no extension. The plain hash is written only inside signed payloads. A reader checks both: the keyed name against the plain hash, and the plain hash against the bytes, inside the core (SY23). |

## 3. Records

### 3.1 Versions

A change file (SP14) carries versions. One version, annotated:

```jsonc
{
  "format": 1,                        // SY9's major format; a higher one is kept aside
  "key": "note:7c1e…",                // SP1
  "device": "a3f0…",                  // its writer, the change file's device (SY9)
  "clock": [1760702400123, 0],        // SP10
  "history": [                        // SY9's version vector, one entry per device
    { "d": "a3f0…", "s": 41, "h": "9b2c…" },
    { "d": "51de…", "s": 7,  "h": "e011…" }
  ],
  "body": { "hash": "5f6a…", "size": 312 }    // the body's plain hash (SP12); or, instead:
  // "deleted": { "covers": [ … ], "identity": { … } }   (SP13)
  // "inline": { … } replaces "body" only in choice: records (SP12)
}
```

| ID | Rule |
|---|---|
| SP10 | **The clock (SY10).** A hybrid logical clock reading is `[ms, n]`: milliseconds since the Unix epoch (48 bits) and a counter (16 bits). Readings order by `ms`, then `n`, then the writer's device ID as bytes, so every device picks the same newest (SY10). A local write sets `ms` to the larger of the system clock and the clock's `ms`, with `n` one more than before if `ms` didn't move, else 0; at `n` = 65535 it waits a millisecond. Applying a remote version moves the clock to the larger of the two, as usual, unless the version is set aside (more than 24 h ahead, SY10), which never moves it. A version more than 5 minutes ahead on arrival marks its device as running ahead (SY10). |
| SP11 | **Version hashes, history and descent (SY9).** A version's hash is `H("linen-sync/version/v1" ‖ JCS(version))`, where JCS is RFC 8785's canonical JSON (integers only, SP3, so no float formatting arises). A version's ID is its writer, its change file's sequence and this hash; a change file holds at most one version of a key, and a version whose `device` isn't its change file's is refused. `history` names, for each device, the latest of that device's versions **of the same key** that this version descends from, and always includes the writer's own previous version of the key, if it had one; so one device's versions of a key form a single line. Version A *descends from* version B when A is B, or A's entry for B's device has a sequence at least B's. An entry is checked against the named device's chain or spine: the sequence must exist, hold a version of this key (by the key hash the spine keeps, SP17) and have this hash. One that can't be checked yet waits; one that is false is refused (SY9). The *heads* of a key are the versions no other known version descends from; two heads with different bodies conflict (SY13), and a version marked wrong-clock or kept (SP12) is left out when heads are ordered (SY10). |

### 3.2 Bodies

| ID | Rule |
|---|---|
| SP12 | **Bodies and the records only the protocol writes.** A record's body is a JSON document stored as a blob (SP9), named in the version only by its plain hash and size, so no change file, shard or device file holds a reader's text (SY11). One kind of record holds no reader text and carries its body in `inline` instead: `choice:‹d›.‹s›.‹h›`, a Keep · Discard choice about one version (SY10, SY34): `{ "choice": "keep" \| "discard" \| "wrong-clock" \| "stop-waiting", "version" }`, where a `keep` names, in `version`, the new version that writes the content again (SY10, SP26); a `keep` counts only once that version is present, descends from the kept one and holds its content, and until then the kept version is ordered as before; or `choice:obj.‹name›`, the reader's Try again for a quarantined object (SY23): `{ "choice": "try-again", "clears": [ { "d", "q" } ] }`, naming the quarantines (SP16) it clears; a new quarantine needs new damage after it. `choice:hold.‹d›.‹s›.‹i›`, the reader's Stop waiting for one hold (SP34): the `i`-th entry (from 0) of the `hold` list in device `d`'s change file `s`, `{ "choice": "stop-waiting" }`. `choice:late.‹d›.‹s›`, the reader's Discard all for a removed device past SP26's cap: every change of `d` after cutoff sequence `s`, fetched or not, `{ "choice": "discard-all", "removal": ‹the hash of the removal whose cutoff `s` is›, "head": ‹a sealed head›, "code": ‹that head's code key's signature over `H("linen-sync/discard-all/v1" ‖ library ID ‖ d ‖ s ‖ removal ‖ head)`, a digest that doesn't include the signature itself› }`; it counts while `head` is the newest sealed head, or once the change file carrying it is accepted by all (SP29), so a choice made with the code current at the time stays valid after the code changes, while a code that a later removal replaced can't authorise a new one. It counts only with that signature, since it discards changes no device has seen and so can't be undone like the other choices; no device fetches or offers that tail again. It discards only what lies after the cutoff that counts: when a later cutoff for `d` counts (SP20), the changes up to it stand, whatever this choice said, and it covers only what comes after the new cutoff. Holds and reservations are entries in change files, not records (SP33, SP34). A choice record is merged like any other: two different choices made apart conflict and the item is offered again (SY10). A choice that lets something go (`discard`, `discard-all`, `wrong-clock`, `stop-waiting`) is treated, on every device that applies it from another, as a deletion of what it lets go: SY26 counts it, the undo journal keeps what it replaced, and the content it frees is retired as a deletion's is and kept for the week (SP36). So a device that signs such choices without the reader can do no more than it could by deleting, and the reader can undo it. |

The bodies, with their SY28 limits:

| Key | Body | At most |
|---|---|---|
| `place:‹book›` | `{ "cfi", "fraction", "chapter" }` | 8 KB |
| `annotation:‹uuid›` | A9's Web Annotation JSON (anchors, colour) | 4 MB |
| `note:‹annotation uuid›` | `{ "text" }` | 4 MB |
| `setting:‹key›` | `{ "value" }`, checked against the key's schema (SY15, SY28) | 64 KB |
| `bookSetting:‹book›:‹key›` | `{ "value" }`, likewise | 64 KB |
| `book:‹book›` | `{ "syncId", "aliases": [sync IDs] }` (SY8) | 1 MB |
| `bookFile:‹book›` | `{ "hash", "size", "title", "authors", "language", "identifier", "layout" }` (SY16) | 1 MB |
| `bookRead:‹book›:opened`, `…:finished` | `{}` and `{ "finished": true \| false }`; the time is the version's clock | 1 KB |

A book's highlights and notes are held to 64 MB in all (SY28); a local note over its limit isn't published (SY28).

| ID | Rule |
|---|---|
| SP13 | **Tombstones and causal frontiers.** A deletion is a version with `deleted` instead of `body`, and stays for good (SY17). `deleted.covers` is the causal frontier SY13 and SY18 require: for each device, the ID of the latest of its changes to the thing (for a book, to anything in it) that the deleting device had seen, `{ "d", "s", "h" }` with `h` the *change file's* payload hash (a change frontier, not a version ID). Each entry is checked against the named chain: the change file at `s`, or its spine entry (SP17), must exist with that payload hash; one that can't be checked yet waits, and one that is false is refused (SY13, SY18). A version of the thing by device `d` lies outside the frontier when its sequence is above `s`, or when `d` has no entry. A book's tombstone also carries `identity`: `{ "hashes": [plain file hashes], "idTitle": H("linen-sync/idtitle/v1" ‖ identifier ‖ 0x00 ‖ folded title) }`, so a file that turns up later is matched by SY8 without the tombstone holding any text. Deleting a highlight whose note is live writes, in the same change file, a tombstone for that note too (SY13), and the view's `week` for the highlight names the note's last body as well, so a Restore brings back the highlight with the note deleted with it (SY19). A note already deleted on its own is left as it is: no second tombstone, and a Restore of the highlight leaves it deleted. |

## 4. A device's chain

| ID | Rule |
|---|---|
| SP14 | **The change file.** Payload `{ "type": "change", "format": 1, "library", "device", "writer", "seq", "prev", "versions": [ … ], "reserve": [ … ], "hold": [ … ] }`, signed by its device with `seq` in the signature (SP6). `prev` is the payload hash of the device's change file `seq − 1`, or null for 1 (a rotated identity starts at 1 and names its predecessor in `trust/`, SP27). `reserve` and `hold` are SP33's and SP34's entries. A file whose `prev` doesn't match the chain the reader holds is refused; one whose sequence is beyond a gap waits for the gap. |
| SP15 | **Publication is crash-safe (SY7).** Local changes are journalled without a sequence. To publish, a device (1) reads its own `changes/`, `devices/` and `state/` files as this pass found them and compares them with its marks (SY7's restore and staleness rules); (2) numbers and signs the next change file; (3) writes the new sequence, hash and the signed bytes to its device store (SP28) and syncs it; (4) only then uploads. After a crash it uploads the stored bytes again, never re-signs that sequence. Device-file counters, view generations and rotations follow the same order, so an honest device never signs two payloads for one place, unless its device store, its library and what it sees of storage are all rolled back together (SP30's limit). A device keeps the signed bytes of each file it has published until a view it has published covers them. **The peer cache (SY7).** It also keeps, for every enrolled device whose files it has accepted, the signed bytes SY7's healing needs: that device's latest accepted device file and view (index and parts), its change files newer than that view, the overflow files its device file names (SP16), and the `trust/` records; at most 32 MB of change files per peer and 256 MB for a peer's view (both prov.; past either, this device stops receiving from that peer before fetching more, and Settings › Sync names it). Peer files leave the cache once a newer view of that peer, accepted here, covers them, except a view that a removal or a merge's `keeps` names (SP26, SP19) and its parts, which stay for good, as in storage (SP36). When storage has shown files older than this device's marks, or lacked ones they name, for an hour, the pass re-uploads its own files and the cached ones (SP37 step 10); their signatures make the copies as good as the originals. |
| SP16 | **The device file (SY7, SY17, SY23, SY34).** Payload, signed with `seq` = `counter`: `{ "type": "device", "format": 1, "library", "device", "writer", "counter", "key", "name", "clock", "head", "own", "view", "frontier", "inherited", "views", "ages", "marks", "refused", "repairs", "quarantined", "proofs", "overflow" }`. `counter` rises by one on every write. `key` is its Ed25519 public key; `name` the platform's name for it, cut to 64 characters (SY7); `clock` its clock when written, and whether it is marked as running ahead (SY17). `head` is the membership head it has accepted (SP20). `own` is `{ "s", "h" }`, its latest change, or null before its first; `view` its newest view's index hash, or null before its first compaction. `frontier` lists, for every other device whose changes it has applied, `{ "d", "s", "h", "sig" }`, where `sig` is that device's own signature from its change file (SP6), so the entry proves itself (SY34). `inherited` lists, for each device, the accepted-by-all mark (SP29) this device holds, `{ "d", "s", "h" }`, resolving like a frontier entry. Wherever a rule asks what every enrolled device's frontier includes, a device's frontier for `d` counts as at least its own `inherited` entry for `d`: a device can vouch this way only in its own place, as its frontier already does, so a just-enrolled device that hasn't caught up still carries the history everyone had accepted, in a signed file a later recovery can read. `views` lists the view index it has accepted for each device. `ages` and `marks` are SP35's. `refused` lists `{ "name", "hash" }` for objects it found damaged (SY23), `repairs` lists `{ "name", "hash" }` for objects it re-uploaded, and `quarantined` lists `{ "name", "q" }` for each object it has quarantined, where `q` is this device file's `counter` when the quarantine first appeared, so a quarantine is named by device and `q`. Times are never sent: each device measures them itself from when it first saw an entry. Damage counts as *again* only from what a device has seen itself: an object it has read and found good, after first seeing a `repairs` entry for it, and then finds damaged within 24 hours by its own vouched-for time, is quarantined and listed. A marker that arrives before the repaired file, or a repaired file before its marker, therefore never counts. Each device also repairs any one object at most once in 24 hours by its own clock, whatever it has seen; a device that sees a peer's `quarantined` entry stops fetching and repairing that object too, until the reader's Try again on any device clears it everywhere: a `choice:obj.` record (SP12) naming the quarantines it clears, so a later quarantine of the same object, which it doesn't name, still stands, and a delayed device file repeating a cleared one changes nothing. `proofs` relays equivocation proofs (SP30). A list (`frontier`, `inherited`, `views`, `ages`, `marks`, `refused`, `repairs`, `quarantined`, `proofs`) that would push the file past 256 KB goes into overflow files. `overflow` is a list of `{ "field", "part", "hash", "size" }`; the file `devices/‹device›/‹hash›.json` is `{ "field", "part", "items": [ … ] }`, and the field's whole list is the field's items in the payload (if any) followed by the items of its parts in `part` order, each part checked against its hash. A copy that a proof relies on (SP30) is an overflow entry with `field` `"copy"`, whose file is the copied file's exact bytes, named by their hash; a proof's `copy` is that hash. |
| SP17 | **The view: index, shards and spine (SY11).** A view is one generation: an index, written last, and parts written first under `state/‹device›/‹index hash›/`, never changed afterwards. The index's payload, signed with `seq` = `gen`: `{ "type": "view", "format": 1, "library", "device", "writer", "gen", "prev", "through": { "s", "h" }, "shards": [ { "lo", "hi", "hash", "size" } ], "spine": [ { "from", "to", "hash", "size" } ], "open": { "hash", "size" } }`. `through` is the last change file it includes, so the index is chained to the device's history; `prev` is the previous generation's index hash. A record goes in the shard whose `[lo, hi]` holds the first two bytes of `H(key)`, read as a big-endian number; shards cover 0–65535 without gaps or overlaps. A shard is `{ "records": [ { "key", "version", "week" } ], "marks": [version IDs] }`: the device's own latest version of each key with its `history`; for content one of its versions *retired* (stopped naming) in the last 7 days, `week` names that content with the retiring version's ID: for a deletion, the last body and, for a book, the bodies of its highlights, notes, place and per-book settings; for a replaced book file (SY16) or an edited body, the previous file or body; so cleanup counts them as named (SY11, SY16, SY17); `marks` are SP35's past-the-week marks for keys in that shard. A spine part is `[ { "s", "h", "p", "sig", "v" } ]`: for each change file the view replaced, its sequence, payload hash, its `prev` (`p`, which the change's own signature covers, SP6, so consecutive entries can be checked to link without the payload), its signature (SP6, so frontier entries for it can still be made, SP29), and in `v` the base64url of 48 bytes per version (16 bytes of `H(key)`, then the version hash), about 70 bytes a version and 86 a change file. `open` is the device's protocol state through `through`: every reservation and hold of its own that hasn't ended (SP33, SP34) and every rotation it succeeded (SP27). A reader that takes a device's changes from a view takes all of them, so a frontier through that view means the hold or reservation was seen. Each part is at most 8 MB (prov.). |
| SP18 | **Reading a peer (SY11, SY34).** For an enrolled device, a reader takes, in this order: its device file (the highest valid counter; a lower one or a conflict copy is ignored); if what it has *applied* of that device is older than the view's `through`, the view named by the device file or, failing that, the newest valid index found by listing; then the change files after what it has applied, or after the view's `through`, in sequence. A device keeps two marks per peer: what it has applied (its `frontier`, SP16) and its *floor*, the newest signed state it knows of (from earlier passes or an enrollment checkpoint, SP24): a change `{ "s", "h" }`, a view generation and a device-file counter. A floor refuses what contradicts it, not what comes before it: a change file at `s` with another hash, a chain that doesn't lead to `h`, a view or device file older than the floor's, or a device file that names a latest change before `s`. Change files and views below the floor are read and applied as usual when their chain leads to it, and the device keeps reading until it reaches the floor; a floor never counts as applied. Every file is checked (size, format, hash, signature, chain) before use and set aside if it fails (SY28). Nothing that contradicts the newest signed state this device knows for that device is accepted (SY34). For a removed device, a reader also fetches the change files after its cutoff, in sequence, at most 500 or 64 MB (SP26's cap), only to list them for Keep · Discard; nothing in them is applied. |

## 5. Membership (`trust/`)

### 5.1 Records

| ID | Rule |
|---|---|
| SP19 | **The claim and the membership records.** Each is a signed file named by its payload hash. Every record but the genesis names `prev`, the head it builds on (`prevs` for a merge). The *head* is a record's payload hash. A *sealed* head is a `genesis`, `remove`, `merge` or `confirm` record: only those carry `code`, `{ "nonce", "codeKey" }`, the recovery code that seals them (SP22), and each is signed by that code's key as well, proving whoever made it holds the code. Nothing else can attach a code to a head: the code is authorised by the same signatures that authorise the record (the first device for the genesis; an enrolled device and the previous code for a removal or merge). |

A removal whose signer was trusted and was only later removed on the same line (by a removal that descends from it) keeps its cutoff: the reader authorised it with the code. The *newest sealed head* is the sealed head that is a descendant of every other sealed head; when sealed siblings exist, there is none until a `merge` seals over them, and meanwhile each branch's code applies the other's removals (SY34). |

### 5.2 The recovery code

| ID | Rule |
|---|---|
| SP22 | **The code, its keys and the naming key's escrow (SY3, SY34).** A code is 26 random Crockford base32 characters (130 bits; from the CSPRNG) and 2 check characters (the first 10 bits of `H("linen-sync/code-check/v1" ‖ the 26 characters)`), shown as 7 groups of 4. Input is upper-cased, with spaces and hyphens dropped and `O`→`0`, `I`/`L`→`1`; a check that fails is a typing error, said at once. `root = Argon2id(the 26 characters, salt = H("linen-sync/code-salt/v1" ‖ library ID ‖ nonce))`, with the 16-byte `nonce` of the record's `code`. From `root`, HKDF (no salt) gives the code's Ed25519 signing seed (`info "linen-sync/code-sign/v1"`) and the escrow key (`"linen-sync/escrow/v1"`); `codeKey` is the signing key's public half. The code is bound to the head it seals by that head's record, which names `codeKey` and is signed with it (SP19), and to the library by the salt. The `escrow` record for a head holds the naming key sealed under the escrow key, with associated data `"linen-sync/escrow/v1" ‖ library ID ‖ head`; an escrow that isn't signed by its head's code key, or doesn't open, is ignored, so a stranger's escrow can't replace the reader's. The code is never stored: a device keeps only the public halves in `trust/`. A device joining by code derives `root` for each sealed head's `code` it finds, at most 64 (prov.), until one's `codeKey` matches. |
| SP23 | **Replacing the code (SY34).** At a removal, a confirm or a merge: (1) Linen makes the new code and shows it; (2) the reader types its last group to confirm it was kept; (3) the device writes the new head's `escrow` (it can name the head before publishing it, since the head is the record's payload hash); (4) only then it writes the `remove`, `confirm` or `merge`. Until step 4, the old head is still the newest sealed head and the old code still enrols and removes. An escrow naming a head that never appears counts for nothing and is removed after a day. First setup is staged the same way: the code is shown and confirmed before the genesis, its escrow and the claim are written, so a setup killed while the code is shown publishes nothing (SY34). |

### 5.3 Enrollment

| ID | Rule |
|---|---|
| SP24 | **Enrollment by a short code (SY34).** Each step is its own file, written once and never rewritten. Each payload below also carries SP5's `device` (its signer: the applicant for a request or reveal, the answering device for an answer or `enroll-ok`) and that signer's `writer` token; each side keeps the exact bytes it used and works only from them, and a file that changes under it ends the attempt. |

SP24's steps:

1. **Request.** The applicant writes `enroll/‹applicant›.json`, signed by its new key: `{ "type": "enroll-request", "library", "applicant", "key", "kx", "name", "commit" }`, where `kx` is a fresh X25519 public key and `commit = H("linen-sync/commit/v1" ‖ library ID ‖ applicant ‖ key ‖ kx ‖ na)` for a fresh 32-byte `na`.
2. **Answer.** An enrolled device, when the reader asks it to add a device, keeps the request's bytes and writes `enroll/‹applicant›.‹device›.json`: `{ "type": "enroll-answer", "library", "applicant", "request" (the request's payload hash), "device", "ne" }` with a fresh 32-byte `ne`.
3. **Reveal.** Having read one answer, and only then, the applicant keeps that answer's bytes and writes `enroll/‹applicant›.reveal.json`: `{ "type": "enroll-reveal", "library", "applicant", "request", "answer" (that answer's payload hash), "enroller" (the answering device), "na" }`. It reveals once; to try again it makes a new key, `kx` and `na`. An enrolled device acts only on a reveal that names its own answer's hash.
4. **The code.** Both devices check `commit` against `na` and compute, from the bytes they kept, the transcript `t = H("linen-sync/sas/v1" ‖ library ID ‖ request hash ‖ answer hash ‖ applicant ‖ key ‖ kx ‖ na ‖ device ‖ device's key ‖ ne)` and the code `(the first 8 bytes of t, big-endian) mod 1,000,000`, shown as `472 913`.
5. **Confirmation on both devices.** The enrolled device shows “Allow ‘‹name›’ to sync? Code 472 913 · Allow · Not now” (item 110). The applicant shows the code and “Does ‹device› show this code? · It matches · Cancel” (new here, item 114). Each side acts only on its own reader's confirmation.
6. **Enrollment.** On Allow, the enrolled device writes the `enroll` record (with `sas` = `t`, and `reveal` and `pop` taken from the reveal's file) to `trust/`, then `enroll/‹applicant›.‹device›.ok.json`: `{ "type": "enroll-ok", "library", "applicant", "t", "enrollment" (the record's hash), "checkpoint", "namingKey" }`. `checkpoint` is everything the new device must never go below: the enrolling device's membership head and removals; its own latest change `{ "s", "h", "sig" }`, view index hash and generation, and device-file counter; its frontier, accepted views and accepted-by-all marks (SP29) for every other device (SY34). `namingKey` is the naming key sealed to `kx`: the device makes an ephemeral X25519 key, and HKDF (salt `t`, `info "linen-sync/enroll-seal/v1"`) of the shared secret gives the key for XChaCha20-Poly1305 with a random 24-byte nonce and associated data `"linen-sync/enroll-seal/v1" ‖ t`; `namingKey` is `{ "epk", "nonce", "ct" }`.
7. **Joining.** The applicant, once its reader has said It matches, accepts only an `enroll-ok` that names its `t` and is signed by the key in `t`, whose enrollment names its own key in a membership graph where that key is trusted. Before it reads any library data, it installs the whole checkpoint as its *floors* (SP28), so nothing older than what the enrolling device had can be replayed to it. Floors are not what it has applied: its applied frontier starts empty, and it reads every device from scratch (SP18), from the views the checkpoint names and the change files after them, refusing anything that contradicts a floor. It opens the naming key, removes its files from `enroll/`, and publishes its library as SY29 says. An enrolled key that publishes no device file within a day (its applicant cancelled or vanished) is listed on the enrolling device with Remove; until its first device file it counts in none of SP36's tests.

A request swapped or answered by someone else gives a different `t`, so the two screens show different codes (SY34). Neither side can choose its value after seeing the other's: the applicant commits first, the enrolled device answers before the reveal, and the reveal pins the answer's bytes, so a fake answer can't be changed after `na` is known. A stranger in the folder therefore matches a code with probability one in a million per try; after three abandoned or refused requests in an hour, the enrolled device stops answering for an hour (SY34). Requests older than a day are removed by any enrolled device; at most 8 requests of 16 KB are read (SY34).

## 6. Freshness and equivocation

| ID | Rule |
|---|---|
| SP29 | **Counters and frontiers (SY34).** A device accepts a peer's device file only with a higher counter than the last it accepted, and a frontier entry only once it resolves to a file in the named chain whose hash matches and whose signature (`sig`) is the named device's. An entry that the named chain shows to be false is refused, and its writer named in Settings › Sync. Removing a device drops every frontier entry only it vouched for. Wherever a rule asks whether every enrolled device's frontier includes a change, a device's own changes are included through its `own` (SP16): its `frontier` lists only others, and it has always seen its own; so in a library with one enrolled device, nobody else is waited for (SY11). **Accepted by all.** For each device, a device also keeps the newest change of it that every enrolled device's frontier has included, a mark that never moves back. A new device receives the enrolling device's marks in its checkpoint (SP24) only as floors; it takes as accepted by all only what it verifies itself from signed device files, the latest change of each device included in every enrolled device's `frontier` or `inherited` entry, so a compromised enroller can't hand it an inflated mark. Wherever a rule asks what every enrolled device's frontier includes in order to decide what stands (SY26's undo journal, SP26's and SP30's cutoffs), the answer is at least that mark, so enrolling a device that hasn't caught up yet never makes a change everyone had accepted revertible again. |
| SP30 | **Equivocation (SY34).** Two valid signatures by one device for the same type and `seq` (SP6), for a type that has one (`change`, `view`, `device`, `rotate`, `enroll`) and a `seq` of 1 or more (a `seq` of 0 is a signature with no place in a history, such as the new key's on a `rotate` or a code enrollment's), over different payload hashes are a proof: `{ "device", "type", "seq", "a": { "hash", "sig" }, "b": { "hash", "sig" } }`, checkable with that device's key alone. So is a `rotate` with a `change` signed after it closed the chain: `{ "device", "type": "closed", "rotate": { "payload", "sig" }, "change": { "seq", "hash", "prev", "vroot", "sig", "copy" } }` (the change's signed `prev` and `vroot`, SP6, so its signature can be checked without the file, and a `copy` of the file where the relayer holds it), carrying the `rotate` record's own payload bytes, so `last` is read from signed bytes, and valid when the change's `seq` is above `last.s`; the device is quarantined with the cutoff `last`, and the change is held for the reader as SP26's late changes are. Every device that holds one relays it in `proofs`, and quarantines the device: from then on nothing it signs is applied, whatever the proof's type. Its membership records are decided by what they are, not by when they arrive: a `remove` it signed with the recovery code still counts (removals only take trust away), subject as always to SP20; a `confirm` or `merge` it signed, which sets a new code, counts only if it lies at or below the membership head that every enrolled device's device file names, so an accepted merge stays authoritative and its branches' old codes stay overtaken, while a new one from a quarantined signer counts for nothing; an `enroll` or `rotate` it signed counts only if it lies at or below the membership head that every enrolled device's device file names, and otherwise counts for nothing, on every device alike. Its cutoff is in its change chain: for a `change` proof, the two branches' common predecessor: the proof names both change files (`a` and `b` as `{ "hash", "sig", "copy" }`, where `copy` is the relaying device's overflow file holding that change file's exact bytes, at most 8 MB like the original), and `base`, the common predecessor `{ "s", "h" }` the relaying device found, with `ancestry`: copies of each branch's change files from `base` to the fork, packed into *bundles* (overflow files with `field` `"bundle"`, each `{ "field", "part", "items": [ base64url of one file's exact bytes ] }`, at most 8 MB after encoding, so a few overflow entries cover thousands of files; a file too large for a bundle goes in a `copy` of its own, its exact bytes), `ancestry` naming the bundles and copies by hash (past 32 MB or 4 bundles (prov.), the spine parts covering them together with the signed view indexes that name those parts, so every link is covered by the forking device's own signature, where such a spine exists; where none does, as many bundles as the ancestry needs), so any device can follow both chains to `base` and check that it links to its own, and each device follows `prev` back from each, through the files or the spine (SP17), to the latest change both share; until it has, it applies nothing more of that device and uses the accepted-by-all mark (SP29) as the cutoff, reverting and holding what lies beyond it, with its undo data kept; once the ancestry resolves to a later common predecessor, what lies between is applied again, and only what follows that predecessor stays held. The cutoff is never earlier than the accepted-by-all mark. Every device reaches the same predecessor, because it is fixed by the two signed payloads; for a `rotate` proof, the `last` both rotations name, read from their payloads, which the proof then names (`a` and `b` as `{ "hash", "sig", "copy" }`, each `copy` an overflow file with the rotation's exact bytes); if their `last` differ, the two `last` changes are a fork of the change chain, and the cutoff is their common predecessor, found as for a `change` proof below, the proof carrying the same `base` and `ancestry`; for a `device`, `view` or `enroll` proof, whose `seq` is a counter, generation or count rather than a change sequence, the latest of its changes that every enrolled device's frontier includes. What of it lies beyond the cutoff and is not yet in every enrolled device's frontier is reverted and held for the reader, except on a record that a device not quarantined has changed since, which is left as it is (SY34). **Its limit:** a device restored from a backup, with its device store, its library and what it sees of storage all rolled back together (a same-Mac Time Machine restore while the storage hides the newer files), can't tell it has been here before and may sign a second file for a sequence. SY7's mark check catches every other restore. When that happens, the proof quarantines an honest device. Nothing is lost: its forked changes are held for the reader (Keep · Discard), and the device, seeing a proof against itself, rotates (SY7) and goes on under its successor. A quarantined identity's `rotate` counts only if it is also signed by the current code's key (the reader enters the code on that device) and its `last` is exactly the cutoff, so everything up to the cutoff still stands and nothing after it does; nothing else it signs counts, so the key that forked can't hand itself a fresh identity. |

### 6.1 A device that missed a removal (#86)

#86 asks whether a device that hears from no other enrolled device should stop applying deletions, and whether any freshness source outside the folder is acceptable under D1. What a device can know: if the storage, or someone who controls what one device sees of it, hides a removal and holds the removed device's key, every file that device sees is consistent and correctly signed. Nothing inside the folder can show it the removal. Any outside source of time or state (a time server, a Linen service) would send something from the device without the reader choosing it, which D1 and P§20 rule out. The one outside channel that sends nothing is the reader, at the device.

| ID | Rule |
|---|---|
| SP31 | **What already bounds it.** (a) While the removal is hidden, the other devices' frontiers, as this device sees them, never include the removed device's later changes, so this device's undo journal keeps every one of them (SY26 keeps a change until every enrolled device's frontier includes it): when the removal reaches it, it reverts all of them (SP26). (b) SY26's counting and SY27's backups bound what can be applied before then. (c) New here: the device that made a removal names in Settings › Sync each enrolled device whose device file doesn't yet name a head including it (“‹device› hasn't caught up with removing ‹removed device› · Open Linen on it”). |
| SP32 | **Out of touch (proposed, item 113).** For each change from device W, this device's *witnesses* are the enrolled devices other than itself, W and the devices W enrolled (directly or through others), since those could be keys in the same hands. When this device has witnesses and has accepted no rising counter from any of them for 7 days by its vouched-for time (SY17; prov.), it is *out of touch with W*: W's deletions, book-file replacements and changes to existing highlights and notes wait, unapplied and counted, and Settings › Sync asks once: “Linen hasn't heard from ‹witness› for 9 days. ‹W› removed 3 notes and changed 5 · Apply · Not now”. Apply is the reader's own word that nothing was removed, and counts as hearing from a witness for another 7 days. Additions, places, reading states and settings apply as usual, still under SY26. A library with no witness for W (two devices, or W enrolled every other) gets only SP31, with one addition: W's deletions and replacements keep their undo data and the local copies of what they retired (SY17's `Backups/deleted/`) for 30 days (prov.) beyond SY26's rule, so a removal hidden for up to a month can still be undone in full; at most 500 changes or 1 GB per writer (prov.), past which W's further deletions and replacements wait for the reader as above. A removal hidden for longer is the limit §8's risk 5 accepts. |

SP32 doesn't stop an attacker who holds the removed device's key *and* the key of a witness, for example the device that enrolled it, if both were removed. That needs two removed keys and control of what one device sees of the storage. SP31 still holds then: the damage is bounded and reverted when the removal arrives.

## 7. Reservations, holds and cleanup

| ID | Rule |
|---|---|
| SP33 | **Reservations (SY11).** Before uploading a blob or a book, a device publishes a change file whose `reserve` lists `{ "kind": "blob" \| "book", "name", "size" }`, and names the object in a later change. A device that finds the object already in storage but named by no live version doesn't rely on it: it treats naming it as a Restore and sends a hold first (SP34). Whatever it uploads, it keeps a copy until every enrolled device's frontier includes the naming change and it has since seen the object in storage, and it uploads it again if a cleanup that raced the upload removed it (SY23's repair). A reservation is refused (before anything is fetched) past 20 or 5 GB open at once for its device (prov.). It lapses 7 days after the other devices first see it, unless named (SY11), and only once this device has read every change file of its writer listed in storage, so a naming change published just before its writer was lost still keeps it. |
| SP34 | **Holds (SY11).** A device about to name content that no live version names (a Restore, an undo, a Keep) publishes a change whose `hold` lists `{ "kind", "name", "hash", "size", "for" }` (`for`: the record key it will name it in), keeps a copy of the content on the device, uploads it again if storage lacks it, and publishes the naming change only once every enrolled device's frontier includes the hold. A hold ends when every enrolled device's frontier includes its naming change, when the reader discards that change (a `choice`), after SY11's 7 dangling days, or, for a removed writer's hold, only by the reader (a `choice:hold.` record with `stop-waiting`, SP12). At most 200 holds or 2 GB per device (prov.). |
| SP35 | **Ages and marks (SY11, SY16, SY17).** `ages` in the device file lists, for each retiring version (a deletion, a replaced book file, an edited body; SP17) whose retired content isn't yet removed, `{ "v": that version's ID, "ms" }`: how long this device has known it, by time it can vouch for. A device marked as running ahead, or whose wall clock jumped by more than 5 minutes against its monotonic clock, publishes no `ages` or `marks` until it is clear. Once its own age passes 7 days, the version's ID goes in `marks` for good (in the device file until the next view, then in that view's shard). A reader adds to a reported age the time since it received that device file, by its own vouched-for time. |

SP36, the cleanup test: a device may remove a blob or a book from storage only when **every** line holds, each checked by this device from signed files it has verified:

1. This device has read every enrolled device's changes through the `own` that device's newest accepted device file names (SP16), and every change file of it listed in storage after that (a writer may have published a change and been lost before its device file), and every removed device's late changes it can fetch (SP18), so no version it hasn't seen can still name the content; content that a late change waiting for the reader names counts as named; and while a removed device has late changes beyond the cap that this device hasn't fetched and the reader hasn't discarded (`choice:late.`), nothing at all is removed from storage, since a later cutoff could make one of those changes stand and any content could be what it names; Settings › Sync names that device with Discard all (SY34); and no live version names it, nor any view's `week` (SP17), hold or open reservation (SP33, SP34). A `week` entry stops counting once lines 2 and 3 hold for the retirement it names, and an `open` hold or reservation once it has ended or lapsed (SP33, SP34), so a view kept for good doesn't keep content for good.
2. For content a version retired (a deletion, a replaced book file, an edited note or highlight; SP17): every enrolled device, this one included, reports an age of at least 7 days for that version (SP35), and this device's own age is at least 7 days.
3. Every enrolled device's frontier includes the change that retired it, and the hold that last held it, if any, has ended.
4. No enrolled device is named as holding cleanup back (silent 30 days, or writing for 7 days without taking in others' changes, SY11).
5. For an object nobody reserved or named: 7 days have passed since this device first saw it, and every enrolled device has since published a device file that this device first saw at least 7 days after that sighting, with this device having read its changes up to the `own` that file names and found no reservation, hold or version naming the object.

Failing any line, the content stays. The view generation a removal or a merge's `keeps` names (SP26, SP19) is kept for good; another generation goes only once every enrolled device's `views` includes a newer one (SY11).

## 8. One pass

| ID | Rule |
|---|---|
| SP37 | **Order, inside SY2's budgets.** (1) Load the device store; check the hardware UUID, the writer token and the marks (SY7). (2) List `libraries/` and `trust/`; read and verify membership (SP20, SP21). (3) List `devices/`; read the device file of each enrolled device (at most 32) and, for at most 32 identities membership doesn't hold, only their device file and `enroll/` request (SY34); for a removed device, its change files after the cutoff, within SP26's cap, to list them (SP18). (4) For each enrolled peer that is ahead: its view if needed, then its change files, in order (SP18). (5) Fetch the blobs the new versions name, checking each (SP9, SY28). Repair (SY23): for every blob or book a live version names that is missing from storage or fails its check there, and of which this device holds a validated copy, upload the copy (temporary name, then rename) and list it in the device file's `repairs` (SP16); a book's upload waits for step 7's budget. An object damaged again within 24 hours of a repair is quarantined, as SP16 says. Before the first pass that applies anything to this library on this device, take SY27's backup (under the lock, at step 6), whatever the pass holds. (6) Small things first (SY22): take the store's write lock; if what follows applies a remote deletion, take SY27's backup under that lock (or rely on the hour's backup only if it already holds every row the step could remove); then, still under it, merge and apply every version but `bookFile` ones in one transaction under the store's lock, keeping undo data (SY26, SY32). SY26's guard is checked before each version: its counts (rolling 24 hours and since the reader last answered, across passes) are updated as versions are applied, and the version that would cross a threshold is not applied; the transaction commits what came before it, and the rest of the pass's remote versions wait, unapplied, until the reader answers (“… · Remove · Stop syncing”). Step 8 runs the same guard on every version it applies, the records that waited for their book included, and counts book-file replacements and removals the same way, and step 7 asks before downloading the file that would cross the additions threshold (SY26). A record whose book hasn't arrived waits with that book (SY24). (7) Fetch the book files the new `bookFile` versions name, each through the importer (SY23), within the day's budget and the disk floor (SY24, SY25); a book that can't come now waits, and nothing else waits for it. (8) Take the lock again; before a `bookFile` version that replaces or removes a file is applied, take SY27's backup under it, likewise; then apply the books that arrived, in a transaction of their own, with the records that waited for them, and release it. (9) Publish: reservations and holds first, then uploads, then the naming change (SP15, SP33, SP34). (10) Write the device file; if storage has been behind this device's marks for an hour, re-upload its own and its cached peer files (SP15). (11) At most once a day, compact (SP17), then clean up (SP36). Each backup is taken under the same hold of the lock as the apply it protects, so the copy and the change agree (SY27); nothing but steps 6 and 8 holds the lock. A budget that runs out stops the pass where it is, after what step 6 has applied (SY2). |

## 9. What it protects, and what it doesn't

| Who | Can | Can't |
|---|---|---|
| Someone who can write to the folder but holds no enrolled device | delete files (never a deletion, SY21); put back older signed files (refused: counters and marks, SP21, SP29); swap an enrollment request (the codes differ, SP24); fill the folder (budgets, SY2) | add a device, forge a change or a removal, or make a device adopt a library it didn't join (SY11, SP24) |
| The storage itself, showing one device an old world, with a removed device's key | have that device apply the removed device's changes until the removal reaches it, within SY26 and SP32 | keep them once it does (SP31) |
| A lost or stolen enrolled device | sign changes until removed; read the folder as long as its account is signed in (item 108) | remove other devices or rotate the code (it doesn't hold the code); outlast its removal, or keep a device it enrolled (SP20, SP26) |
| A misbehaving enrolled device | equivocate (proved and quarantined, SP30); claim false history or frontiers (refused, SP11, SP29); report false ages (never shorten another device's Restore, SY17, item 111) | silently drop another device's edit (SP11) |
| The provider extension | see names and opaque handles | read a body, a book or a key; confirm a known book or note from its name (SP9, SY3) |
| Whoever holds the recovery code | enrol and remove devices; read the naming key | it is the reader's second root, by design (SY34) |
| Code running as the same macOS user | anything Linen can do (SY34) | outside what signing protects (SY34) |

## 10. For the reviewers

New here, beyond what the plan already says:

- **Item 114:** the applicant confirms the code too (SP24 step 5). Without it, a stranger in the folder could answer an applicant with a fake library of its own and send an enrollment at once; the plan's flow asks only the enrolled device.
- **Item 113 (#86):** SP32's out-of-touch rule; SP31's (c), naming devices that haven't seen a removal, is a new status line.
- Names are lowercase only (SP2), a subset of SY2's set.
- The spine costs about 70 bytes a version (SP17), not the plan's “tens of bytes”.
- `enroll/` holds four files per attempt, not SY34's two, each written once (SP24): a rewritten answer could be changed after the reveal.
- A device ID is derived from its key (SP1), not drawn on its own; SY7 in the plan is amended to match.
- A code is bound to its head by the head's record, which names the code's public key and is signed with it, rather than through the key derivation (SP19, SP22), so the code can be authorised by the same signatures as the record.
- SY7 says a restored Mac “reuses no sequence”. That holds unless its device store, its library and the storage it sees are all rolled back together; SP30 says what happens then.
- Replaced book files and edited bodies are retired as deletions are and kept for the week (SP17, SP36), as SY16 and SY11 require.

**Codex's local review (2026-10-17, before the PR)** found nine problems in the first draft; each is fixed above: seals that anyone could make (now SP19's sealed records); a reveal that didn't pin the answer, which let a fake answer be ground to a chosen code (SP24 step 3); no checkpoint of the enrolling device itself (step 6); views that dropped holds and reservations (`open`, SP17); spines without the signatures frontiers need (SP17); replaced book files cleaned up within the week (SP17, SP35, SP36); a full rollback making an honest device equivocate (SP30's limit); rotation renaming signed references (SP27); and derivations too loose to build twice the same way (SP4's exact inputs).

Questions for the security review:

1. Is signing the payload hash with its type, library, signer and sequence (SP6) enough to rule out a file signed for one purpose being accepted as another?
2. Does SP20's membership computation let any record, valid on its own, restore trust in a removed device, or let a removal be undone by a sibling branch?
3. Is SP24's commit-then-reveal sound against a stranger who controls the whole `enroll/` area, with SP24 step 5 on both devices?
4. With 130-bit codes, is Argon2id (SP22) worth its cost on an iPad, and are the parameters right?
5. Does SP36's checklist leave any order of delivery in which content a live version names is removed (Stage 1's three-device check)?
6. Is SP32's definition of a witness the right trade between catching a hidden removal and asking the reader too often?
