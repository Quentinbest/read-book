# Sync across devices — plan

Status: approved by the owner 2026-10-17 (#84; `docs/decisions.md`), drafted 2026-10-16 for #73. Stages are #91 (Stage 0) to #97 (Stage 6). Nothing here is built. Values marked (prov.) are provisional until the owner approves them, as in `docs/implementation-plan.md` §1.2. The open questions are items 98–111 in `docs/pending-approvals.md`; nothing that depends on one is built while it is open.

Sync lets one reader keep their place, highlights and notes, settings, library list and books the same on every device they use, through storage they already have: their iCloud Drive or Google Drive folder. It comes as provider extensions in a new sync slot of the Host API, the two providers listed as Built-in. This file is the rule register that code and tests for this work cite (`// SY14: …`). It doesn't change `docs/implementation-plan.md`, which stays read-only.

**When it is built.** The owner decided on 2026-10-14 that sync waits for a second platform (#54, #80). After this plan merges, each stage in §6 gets its own sub-issue of #73, unlabelled; a stage is built when the owner labels it.

### 1.2 What syncs (Decision 10-14)

| Syncs | Stays on each device |
|---|---|
| The place in each book | Extensions: packages, on or off, grants, storage, keys |
| Highlights and notes | MDX dictionaries and their order |
| Settings, the ones SY15 lists (item 103) | Device-only settings (SY15), and the sync setup itself |
| The library list: which books, last opened, finished | Covers and the search cache, which are rebuilt from the book |
| The books themselves (EPUB files) | The crash log (D1) |

### 1.3 Out of scope

- Accounts, or storage run by Linen (P§20; Decision 10-14).
- Syncing extensions or MDX dictionaries (Decision 10-14).
- Building other platforms (#54, #80).
- Other providers (WebDAV, Dropbox and others). The slot leaves room for them (SY3); none is built.
- Encryption by Linen of what is in storage (item 108).
- Sharing between different readers, and syncing to two storages at once (item 109).
- Versions or history beyond the week that deleted things are kept.

## 2. What is there today (read 2026-10-16)

- **The store** (`src-tauri/src/store.rs`, schema 5). Books have a local UUID, a unique `content_hash` and the OPF `package_identifier`. A book's place is `positions` (CFI, fraction, `updated_at`, chapter label). Annotations already have global UUIDs, `created_at`, `updated_at` and `deleted_at`. A deleted annotation stays, marked, for Undo, and goes only with its book. `settings` is keys and values. `book_settings` and one setting key (`simplifyStyles:<bookId>`) name local book IDs, which differ on each device.
- **Removing a book** (G4): `remove_book` marks it; the next launch's `purge_removed` deletes the row, its annotations and place (cascade), its file and its cover.
- **Import** (`src-tauri/src/import.rs`): B3 and B3-guard. The same hash means the book is already in the library. The same identifier and title (case and spacing ignored) with a different hash means an updated file: the copy is replaced and annotations re-anchor when the book opens. Anything else is a new book.
- **The library folder** (D2): `~/Library/Application Support/app.linen.reader/`, holding `Books/`, `Covers/`, `Extensions/`, `Dictionaries/` and the database. Files are found by name inside it, so a restored folder works anywhere (`Library::book_file`).
- **Extensions**: Host API 1.2.0 (`manifest.rs`). Built-ins are compiled in (`ext_commands.rs` `BUILTINS`), have IDs starting `app.linen.`, and can be turned off but not removed (G7). Markdown Export holds `annotations.read` and `files.export`. Manifests refuse unknown fields, so a provider manifest needs a Linen that has the slot. An extension has no file system; `files.export` reaches only a file the reader picks in the system dialog.
- **The app is not sandboxed** (no entitlements file), so the core can reach `~/Library/Mobile Documents` and `~/Library/CloudStorage`. macOS may still ask the reader's permission first (Stage 0 finds out).
- **The test build** honours `LINEN_DATA_DIR`, so the in-app suite can run two library folders, one after the other, against one storage folder.
- **Nothing is sent anywhere** (the README's Privacy section; D1).

## 3. Decisions this plan rests on

Settled (Decision 10-14 and earlier):

- Everything in §1.2's left column syncs; extensions and MDX dictionaries do not.
- Linen runs no storage. It uses the reader's iCloud Drive and Google Drive, by writing into their folders on the Mac. No iCloud container, Apple Developer account or Google API.
- Sync comes through the sync slot (P§18, P§20). The iCloud and Google Drive providers come with Linen, listed as Built-in, like Markdown Export.
- When two devices changed the same highlight or note while apart, the reader decides which to keep.
- A deletion removes the local copy first, then the copy in storage. What was deleted is kept in storage for one week and can be restored during it. A device away for more than a week does not bring it back.
- Nothing leaves the device unless the reader chooses it (D1). Extensions reach the file system only through the host and its permission check (P§19, plan §7.2).
- B3 and B3-guard decide which book is which. A9 stores highlights as W3C Web Annotation JSON with two anchors.

### 4.1 The slot, the folders and the providers

| ID | Rule | Source | Stage |
|---|---|---|---|
| SY1 | **The sync slot (Host API 1.3).** A manifest may contribute `syncProviders: [{ id, title, description }]` and needs the permission `sync.provider` (item 98). It activates on `onSync:<id>`. In its Worker, `linen.sync.registerProvider(id, { list(prefix, cursor), read(name), write(name, body), remove(name) })` makes it a store of named objects. A provider never merges, decides or reads Linen's data: the core keeps the journal, merges, conflicts and the week (§4.2–4.4) | P§18, P§20; Decision 10-14 | 2 |
| SY2 | **The brokered folder (item 98).** `folder:icloud-drive` and `folder:google-drive` give `linen.folder.list`, `.read`, `.write`, `.remove` and `.stat`, confined to a `Linen` folder at the top of that storage, which the host finds (iCloud Drive: `~/Library/Mobile Documents/com~apple~CloudDocs/Linen`; Google Drive: `~/Library/CloudStorage/GoogleDrive-‹account›/My Drive/Linen`, the account chosen at setup). Paths are relative and at most four segments deep; no `..`, and no symbolic link is followed. A name the extension makes up (to write) is `[A-Za-z0-9._-]` only, with no hidden names. A name the storage made (a conflict copy such as “changes 2.json” or “state (1).json”) can only come back from `list`, as an opaque token the host issued; `read` and `remove` accept that token, and `write` never does. A write goes to a temporary name and is renamed. `list` returns at most 1,000 names a page, with a cursor. Each pass has budgets (prov., item 106): at most 100,000 names listed, 32 devices, 256 MB read apart from book files, and 60 s. Before a device is enrolled, Linen reads nothing from storage but that device's own `devices/` file, the `enroll/` area, `libraries/` and `trust/` (SY34), each within the budgets, and a set-aside list of at most 1,000 names is kept. When a budget runs out, the pass stops where it is and Settings › Sync says the storage holds more than Linen expected; past the set-aside limit, sync pauses until the reader looks. A book file has no size cap of its own: its zip central directory is read first and the importer's limits (plan §7.1: entries, uncompressed size, ratios) applied before the rest of the file is read, so sync accepts exactly the books the importer does (SY23); other objects over 16 MB (prov.) are refused; SY28 sets tighter limits per type | P§19, plan §7.2; Decision 10-14 | 2 |
| SY3 | **Handles, not bytes.** Object bodies cross into the Worker as opaque handles: `read` returns one and `write` takes one, so a folder provider passes handles from `linen.sync` to `linen.folder` without ever seeing a book, a note or a setting. The host moves the bytes and checks each object's hash (SY23). Reading a handle's bytes in the Worker, which a network provider would need, is reserved and not in 1.3. Object names are opaque too: `books/` and `blobs/` names are a keyed hash of the content (HMAC-SHA256 under a library naming key that enrolled devices receive at enrollment, SY34; `trust/` also keeps the naming key sealed under a key derived from the current recovery code, re-sealed by the device that changes the code, so a device joining by recovery code alone gets it too), so a provider can't confirm a known book or a guessable note or setting from its name; the plain content hash stays inside the signed records, which only the core reads | P§19 | 2 |
| SY4 | **The built-ins.** `app.linen.sync-icloud` (“iCloud Drive”) and `app.linen.sync-google-drive` (“Google Drive”) are listed as Built-in in Settings › Extensions and can be turned off, not removed (G7). Being installed and on doesn't sync: neither activates, and the host opens no file in either storage, until the reader sets that storage up (SY6) | Decision 10-14; G7 | 2 |
| SY5 | **Budgets and safe mode.** Brokered folder and sync calls are the host's work and don't count toward the Worker's 10 s (P6). A file the storage hasn't downloaded yet is waiting, not a failure (SY30). In safe mode (P7) nothing syncs; local changes stay in the journal and go at the next normal launch | P6, P7 | 2 |
| SY6 | **Only storage the reader chose (D1).** Sync runs only after the reader chooses a storage in Settings › Sync (item 99) and confirms a setup sheet that names the folder, what will be copied (“12 books, 840 MB, and your highlights, notes, places and settings”) and who keeps it (“Apple keeps it in your iCloud account” / “Google keeps it in your Google Drive”). With none chosen, Linen opens no file in either storage and sends nothing, as today | D1; #73 | 2, 3 |

### 4.2 Identity and records

| ID | Rule | Source | Stage |
|---|---|---|---|
| SY7 | **Devices.** A device's ID is random, made on first use of sync and kept outside the library folder, in the platform's own per-device store (on macOS, the login-keychain item `app.linen.reader/sync-device`, owner 2026-10-17, item 112: Linen's ad-hoc builds can't use the data-protection keychain's *ThisDeviceOnly* class, `docs/spikes/sync-folders.md`). The ID also records the Mac's hardware UUID (`IOPlatformUUID`); a device that finds a different one, as on a Mac set up by Migration Assistant, takes a new ID. When storage holds changes under this ID newer than the device's own mark (a Time Machine restore of the same Mac), it takes a new ID too. The data-protection item replaces this once a release is shown to carry the keychain entitlement (#53). Every file a device writes also carries a writer token kept with the ID. A device that finds its ID in storage with another token (an ID copied some other way) takes a new ID at once, and it never replaces a file that carries another writer's token. A library folder restored on another device (D2) finds no ID there and makes its own, so two devices never write as one. A library restored on the same device from an older copy is caught too: the device store keeps, beside the key, the last sequence and hash the device wrote, the newest frontier it had accepted for every other device, and the newest sealed membership head and removals it had accepted, and when the library is behind that mark, the device takes a new ID and keeps refusing anything older than those, a removed device included. Storage that shows older files than those marks while the library is current is only stale: it is refused and waited for (SY30), and nothing rotates. If it is still behind after an hour, the device re-uploads the signed files it holds (its own change files, views and device file; the signed `trust/` records; other devices' unacknowledged files; and the latest compacted view and signed `devices/` file of every enrolled device that it has accepted, plus that device's change files newer than that view, which each device keeps a copy of for this until it holds a view covering them; at most 32 MB of them per peer, and a peer's view at most 256 MB in all, shards and spine together (both prov.); beyond either, this device stops receiving from that peer before fetching more, and Settings › Sync names it); their signatures make them as good as the originals, so storage that lost them heals. Any library found behind those marks is treated as a restored backup (SY27): sync starts paused and Resume asks which should win, so a current deletion or replacement can't erase what the restore brought back. Its old key is still in the device's own store (the library folder never held it), so the old identity signs a *rotation* record: the new key takes the old one's place in the membership chain, with its enrollment ancestry, and the devices the old identity enrolled stay enrolled. A rotation is not a removal, so nothing cascades, and frontiers and holds carry over to the new ID. An identity may rotate at most twice in 30 days without the recovery code (prov.), and a retired ID's files are compacted and removed like any acknowledged history. An identity's rotations continue it: a removal of an identity also removes every rotation of it, including one made at the same time as the removal, apart. The device stays enrolled (SY34) with no recovery code needed. Its name comes from the platform (on macOS, the computer name), at most 64 characters, kept in the storage for conflicts and messages; a longer name from storage is cut before it is stored or shown, and a `devices/` file is at most 256 KB. In every membership decision (enrolling, recovery, Remove, Keep) Linen shows instead the label the reader confirmed when the device was enrolled, its enrollment date and a short fingerprint of its key, none of which the device can change. Nothing in the sync format is specific to the Mac | Prototype; D2 | 1 |
| SY8 | **Which book is which (B3).** A synced book has a sync ID (a UUID from the device that first stored it) and an identity: its content hashes, and its OPF identifier with its title folded as B3-guard folds it. Two books are the same when a content hash matches, or when the identifier and the folded title both match. Each device works these out itself from book files it has validated (SY23); aliases in a record are only hints, and two sync IDs merge only when this device's own reading of their files supports it. When two libraries stored the same book under two sync IDs before they first met, the smaller ID wins on every device and the other becomes its alias; highlights, notes and places from both are kept. Local book IDs never leave the device: records name sync IDs, and per-book keys (`book_settings`, `simplifyStyles:<bookId>`) are translated | B3, B3-guard; #73 | 1 |
| SY9 | **Records.** Each synced thing is one record: `place:‹book›`, `annotation:‹uuid›` (a highlight: anchors and colour, as A9's JSON), `note:‹annotation uuid›` (its note, a record of its own, so deleting or emptying a note while the highlight stays (A6) is a deletion kept for SY17's week and restorable), `setting:‹key›`, `bookSetting:‹book›:‹key›` (one per per-book setting), `book:‹book›` (the sync ID, its identity aliases from SY8, added), `bookFile:‹book›` (the current file's hash with everything read from that file: title, authors, language, OPF identifier, layout; SY16), `bookRead:‹book›:opened` and `bookRead:‹book›:finished` (SY14). What a file determines travels with that file, so a merge can't pair one device's EPUB with another's title. Things with different merge rules are never in one record, so a merge of one (a new edition) can't undo another (finished, made apart on another device). A version is `{ format: 1, key, clock, device, history, body }`, or `deleted` in place of `body`. `history` is a version vector (for each device, the latest of its versions of this record that this one descends from), so “descends from” (SY13) is decided from the version alone and never needs an older version to still exist. Each entry names the version it covers by device, sequence and hash, and must be a version the writer could have seen: one in that device's signed chain. A version naming an entry this device can't verify yet waits; one naming an entry that the named device's chain shows never existed (a forged or future ancestor) is refused. So a device can't claim to descend from another's edit it never saw, and silently drop that edit. Unknown fields are kept and passed on unchanged. A record in a newer major format is kept aside, never applied or rewritten (at most 1,000 records or 64 MB of them per device, prov.; at that point this device stops receiving from that device, keeping everything it has, and Settings › Sync says “‹device› uses a newer Linen · Update Linen”), and Settings › Sync says “‹device› uses a newer Linen · Update Linen” | Plan §4; Prototype | 1 |
| SY10 | **The clock, and what “newest” means.** Versions carry a hybrid logical clock. It keeps cause and effect in order: a change made after a device has seen another version always sorts after it, whatever either system clock says. Between concurrent versions (made apart, neither seeing the other), “newest” means the higher clock reading, ties broken by device ID, so every device picks the same one. That reading follows each device's system clock, so a device whose clock runs ahead can win a concurrent change it made earlier. Two guards: a remote version whose clock is more than 5 minutes ahead of this device's clock on arrival marks its device as running ahead, and Settings › Sync says “‹device›'s clock is ahead · Set it to automatic”; one more than 24 h ahead is set aside and applied once the clock catches up (both prov., item 106); at most 1,000 such versions or 16 MB from one device are kept (prov.), beyond which this device stops receiving from it, before fetching bodies, and Settings › Sync names it. When a device corrects its own clock, it re-checks every remote version it applied while its clock was wrong, and one now more than 24 h ahead is treated as set aside after all (reverted from the undo journal and offered as below). Where the journal no longer holds what it replaced, the version isn't reverted: the device signs a resolution that marks it wrong-clock, so every device ignores it when ordering (as after Keep, below), and writes its content again with the corrected clock; Settings › Sync names it for the reader. A device that finds its own logical clock more than 24 h ahead of its corrected system clock (it wrote while its clock was wrong) doesn't wait for time to catch up: it rotates to a new identity with a fresh clock (SY7's rotation), and the versions it wrote with the wrong clock are offered to the reader on every device (Keep · Discard) rather than applied or left set aside. A version that is set aside never moves any device's clock, so no device's clock follows the wrong one. Keep writes the content again as a new version with the corrected clock, descending from the wrong-clock version, which from then on is ignored when versions are ordered; so later changes made with a correct clock, including ones made apart on a device that never saw any of this, win as they should; Discard writes a signed resolution naming the discarded version, so no device offers it again. A choice is itself a record (one per offered version): two devices that chose differently apart conflict like any other record (SY13), and the item is offered to the reader again with both choices shown; until then neither applies. The same holds for every Keep · Discard choice in SY34. Highlights and notes never rely on this: concurrent changes to one go to the reader (SY13) | Prototype; review | 1 |
| SY11 | **The folder's layout.** `Linen/libraries/‹library›.json` (format, a library's sync ID, created): a device setting up an empty folder writes its own claim, never a shared file, and pins that library as its own. A device never adopts another claim on its own: it joins an existing library only by enrollment (SY34). When two devices set up the same folder at once, the second to see the other's claim says “Another device set up Linen here · Join it”, and joining is an enrollment like any other, after which its own claim is removed. A device that has asked to join another library enrols no one into its own, so if two devices ask to join each other's, only the join into the library with the smaller ID can complete, and the other request is refused; `devices/‹device›.json` (name, last sync, format); `changes/‹device›/‹sequence›.json` (each device's changes, in order); `state/‹device›/` (that device's compacted view, at most once a day, after which it deletes those of its own change files that the view includes and that every enrolled device has accepted a view covering (its signed frontier names that view). A change nobody else has acknowledged stays as a file, so it can still be verified link by link and delivered late (SY34). The view also keeps the chain's spine: for every change file it replaced, its sequence and hash and the hash of each version in it (tens of bytes a version, in the shards), so a version another device branched from long ago can still be verified (SY9). The view is split into shards of at most 8 MB (prov.), with records assigned by a hash of their key; `index.json` names the shards with their hashes and the last change sequence the view includes. A reader takes changes up to that sequence from the view, and waits only for missing change files after it, so a device that was behind resumes correctly across a compaction. A new generation of shards is written first and the index replaced last, so a reader never sees half a view. Each generation lives under its own index hash and is never changed: an older generation is removed only once every enrolled device's frontier includes a newer one, and the generation a removal names (SY34) is kept for good; the view keeps each record's latest versions with their `history` (SY9), so a device back with a branch from a compacted version is still told apart from a descendant; it also keeps, for each thing deleted in the last 7 days, its last body and, for a book, its highlights, notes, place and per-book settings, so compaction never shortens SY17's week); `books/‹name›` (the keyed name of SY3); `blobs/‹name›` (keyed as in SY3), holding every record body (quotes, notes, book metadata, settings): versions, change files and shards hold only the body's hash, so no device's own files ever keep a reader's text. Blobs are shared and content-addressed. **Cleanup of stored content (blobs and book files).** A device reserves an object in its own chain before uploading it, and names it in a later change. A device may hold at most 20 reservations or 5 GB reserved at once (prov.); a reservation past that is refused before anything is fetched, and every reservation lapses 7 days after other devices first see it unless named. A reserved object that no change names 7 days after its writer's chain moved past the reservation, or, for a removed writer, once the reader has kept or discarded its late changes or chosen Stop waiting (SY34), and an object that nobody reserved or named, seen so by every enrolled device for 7 days, are removed like unnamed content. Content that any live version names is never removed. Any device may remove content that no live version names only when all of these hold: 7 days have passed since it stopped being named (by SY17's two clocks); every enrolled device's signed frontier (SY34) includes the change that stopped naming it; and no enrolled device holds it. A device about to name content that no live version names (a Restore, SY19, or an undo) first sends a *hold* for it as a change of its own, carrying the content itself (a book's file goes with the hold as its own object), and sends the change that names it only once every enrolled device's frontier includes the hold and the content is again present in storage under its name, re-uploaded from the hold if a device removed it meanwhile. Any device that finds a live version whose content is missing restores it from a hold. A device that has seen a hold never removes that content, so neither a late delivery nor a third device that lags behind can remove it in between. The hold ends once every enrolled device's frontier includes the naming change, or when the reader discards that change (SY34). A removed writer's hold lasts until the reader keeps or discards its late changes; if none has arrived, Settings › Sync says “Waiting for changes from ‹device› · Stop waiting”, and only the reader's Stop waiting ends it; a hold that ends without its naming change leaves the content to the usual cleanup. With one enrolled device there is nobody to wait for. | SY34 | **Signed changes and enrolled devices (item 110).** Each device has an Ed25519 key pair; the private key is kept with its ID (SY7: the login keychain for now, the data-protection item once a release carries the keychain entitlement), and the public key goes in its `devices/` file. Code running as the same macOS user is outside what signing protects against: it can already change the library that Linen signs and syncs, and with ad-hoc builds it can read Linen's login-keychain items (`docs/spikes/j-keychain.md`). The signatures protect against everyone who can write to the storage but doesn't run code as the reader on an enrolled device. Every change file, shard index and library claim is signed by its writer. Each change file also carries the hash of the device's previous one, and each shard index the hash of the last change it includes, so a device's history is one chain and no file in it can be replaced afterwards, and blobs and books are covered through the hashes that signed versions name. A device's key is accepted only when an enrolled device has signed it in. The first device enrols itself. A new device is enrolled when the reader confirms, on any enrolled device, a short code shown on both (prov.), or enters the library's recovery code, which the first setup sheet shows once. A recovery code carries at least 128 random bits (shown as groups of letters and digits), and its keys are derived with a memory-hard function (Argon2id) bound to the library's ID and the head it seals, so the public halves in storage can't be used to guess it offline. With the code, the new device writes an enrollment record for its own key into `trust/`, sealed with the key derived from the code; devices accept a key signed in by an enrolled device or by such a record. A library has at most 12 enrolled devices, and one device may enrol at most 2 others a day (prov.); beyond either, enrollment needs the recovery code, so a compromised device can't flood the library with keys. A code-sealed record names the sealed head it builds on and counts only if that head is still the newest sealed head, and only once a live enrolled device's frontier, signed after the record, includes it, or the reader confirms the new device on this device: every removal rotates the code and makes any code-sealed record on an earlier head, as a sibling of that removal, count for nothing, so an old code can't enrol anyone. The code is a second root of trust, which is why only the reader holds it. Enrollment goes through `enroll/`, the one area an applicant and the enrolled devices both read. It holds at most 8 requests of 16 KB each: `enroll/‹applicant›.json` (its key and commitment, written by the applicant) and `enroll/‹applicant›.‹device›.json` (the enrolled device's answer, then the signed enrollment with its frontier). An applicant may also read `libraries/` and the sealed device list, `trust/`, which is all the recovery path needs. The applicant removes its files once enrolled, and any enrolled device removes requests older than a day. The code is a short authentication string, not a shared secret: the new device first commits to its key and a random value, the enrolled device then answers with its own, and the six-digit code is derived from both keys, both values and the library's ID. A request swapped in the folder therefore shows a different code. After three abandoned or refused requests in an hour, the enrolled device stops offering enrollment for an hour. The protocol gets its own security review in Stage 1. Until it is enrolled, a device's changes are never applied, and never fetched: from an identity the membership chain doesn't hold, Linen reads only its `devices/` file (at most 256 KB) and its `enroll/` request, and looks at no more than 32 such identities a pass, so nothing from it accumulates. So someone who can write to the folder, but holds no enrolled device, can't add a device, forge a deletion or change anything; at worst they can delete files, which SY21 never treats as a deletion. **Freshness:** each device's signed `devices/` file carries a rising counter and, for every device, the latest change of it that it has applied. A device never accepts a view, index or change older than the newest signed frontier it knows. A frontier entry counts only once it resolves to a version (device, sequence, hash) in that device's own signed chain; until then it advances nothing. An entry the named chain shows to be false (a sequence that doesn't exist, or a wrong hash) is refused and its writer is named in Settings › Sync. A frontier entry carries the named device's own signature over its sequence and hash, so two different entries for one sequence are a proof of equivocation that any device can check without the files, and every device that holds such a proof relays it in its own `devices/` file. Two different signed files or entries from one device with the same sequence (equivocation, which an honest device never does) quarantine that device on every device that sees the proof: nothing it signed from that sequence on is applied, and whatever of it was already applied but not yet in every enrolled device's frontier is reverted from the undo journal and held for the reader, as after a removal; a record changed since by a device that isn't quarantined is left as it is. A fork that surfaces only after every enrolled device had accepted the first branch quarantines the device from then on, but what they had all accepted stands (it is no worse than had the device made that change honestly), so no undo data has to be kept for ever, Settings › Sync names it with Remove, and after Remove its changes before the fork stand. Removing a device also drops every frontier entry it alone vouched for. A device being enrolled receives the enrolling device's frontier with the confirmation, so older signed copies can't be replayed to it. Membership is itself a hash chain of signed records in `trust/`: each enrollment is signed by the enrolling device (or sealed by the code, below), and each removal by a device holding the code. The first setup seals the chain's first head with a key derived from the first recovery code, staged as a replacement is (below): the code is shown and confirmed, and only then is anything published, so closing Linen during setup leaves nothing bound to an unseen code; and every removal, which needs the code anyway, seals the head with a key derived from the new code. Removals only ever take trust away, so a device accepts every removal record signed by a device trusted at that record's predecessor, and two removals made apart (sibling branches) merge as their union, except that a removal built on a head that is no longer the newest sealed head counts only once the reader confirms it on a device it doesn't remove by entering the current recovery code (the confirmation is signed with the newest head's code key), whoever signed it, so a stale code can't remove the reader's devices. The next device to see siblings asks the reader for either branch's code and seals one head over both under a fresh code, staged as any code replacement is (below): the reader confirms the new code, the naming key is re-sealed under it, and only then is the head published. A device joining with the recovery code doesn't rely on seeing every branch: it lists the devices the chain it can open still trusts, and the reader confirms which to keep (“Keep ‹device›? · Keep · Remove”) before anything from them is applied. A removal made this way takes as its cutoff the latest change of that device that every other enrolled device's frontier includes, so nothing they had all accepted is reverted, and only what came after it is held for the reader. When no other enrolled device remains (the reader lost the only one), the cutoff is the removed device's history as the recovering device verified it, so the whole library is recovered and nothing of it counts as late. The reader knows which devices they lost, and those choices are removals sealed with the code they entered, so a sibling removal delivered late can't leave a lost device trusted. A device joining with the recovery code accepts the chain from the newest head that code opens and follows the signed records after it. Hiding later records can therefore only hide enrollments, never a removal, and an older chain that still trusts a removed device can't be replayed to it. Its first view of the data may still be older than the newest if files were put back, and with no enrolled device online it can't tell. So until an enrolled device's frontier confirms it, it applies no deletion from that view: deletions are listed for the reader (“Deleted on ‹device› · Keep deleted · Restore”), it applies no change from a device the list doesn't trust, and it never sends a version that brings anything back (SY20). **Removal:** Settings › Sync lists the enrolled devices with Remove. Removing one needs the current recovery code, proved: each code derives a signing key, each sealed head names that key's public half, and a removal counts only if it is signed by the current code's key as well as by an enrolled device. The code is held only by the reader (it is shown, never stored; devices keep only the public half), so a lost or stolen device can't remove anyone. Remove stops a device's changes being accepted, but it can't stop that Mac reading the folder while it is still signed in to the iCloud or Google account, because what is there isn't encrypted (item 108); the Remove sheet says so and tells the reader to sign that Mac out of the account or erase it. It is signed by an enrolled device and names, by sequence and hash, the last change of the removed device that this device had already applied, and the hash of the latest compacted view of it that this device had accepted, as the last still accepted. So only the chain ending there, and only that view, count. Nothing is applied to make a removal: changes of the removed device that storage holds but this device hadn't applied go to the reader with the late ones below. A device that receives a removal reverts every change of the removed device it had applied beyond the cutoff, from its undo journal (SY26), and lists those too; a record changed since by this device or by any device that isn't removed is left as it is, and only its listing records what the removed device had done. The undo journal keeps each change from another device, with the version it replaced, until every enrolled device's frontier includes that change and at least 7 days have passed, so any later cutoff falls at or beyond it, and replaces the recovery code (shown once again). The replacement is staged so a crash can't lose it: the new code is shown and the reader confirms it was kept (by typing its last group), the naming key's seal under the new code is written, and only then is the new head published; until that moment the old code still works. Changes signed by a removed device after that point are set aside everywhere, but not discarded: every change whose chain continues from the cutoff and that the removal didn't include (perhaps written before it and delivered late by the storage; clocks can't tell, SY10) is listed in Recently deleted as “Arrived from ‹device› after it was removed · Keep · Discard”, for the reader. None of them is applied without that choice. Both choices are written down: Discard as a signed resolution naming the discarded version, so no device offers it again, and Keep without applying the removed device's signature: the device where the reader chose writes the change again as its own new version, descending from the late one, holding any content it names (SY11) until every enrolled device has it. Each removed device's late changes are capped at 500 or 64 MB (prov.); beyond that nothing more of it is fetched, and Recently deleted offers “‹device› sent more after it was removed · Discard all”. Each enrollment record names the device that signed it in. A removal also removes every device the removed one signed in, and theirs in turn, so a key a lost device added can't outlive it; it names the same cutoff (last applied change and accepted view) for each device it removes this way. Settings › Sync names them first, and the reader may keep one by entering the recovery code on it, which gives it a new key and ID, enrolled by the code (its old identity stays removed), and its changes after the cutoff go to the reader as late changes. Removals merge as a set that only grows: a device once removed stays removed. When two removals of the same device name different cutoffs, the later cutoff counts: everything up to it had already been accepted by an enrolled device, and nothing is reverted after its undo data may have gone. Since each removal needed the code, two concurrent ones were both the reader's, and both count. After concurrent removals, each branch's head stays sealed by its own new code, and either code opens its branch and applies the other branch's signed removals. If two devices removed each other, both are out and the reader rejoins with one of those codes | Security review | 1, 3 |

### 5.3 How a sync pass runs

```
core engine ──► host ──► provider Worker (list/read/write/remove)
                              │
```

The engine holds every decision. The Worker sees names and handles only (SY3). The host checks each call against the provider's grants, as every Host API call is (P2).

## 7. Edge cases the checks must cover

From the prototype's list, with Decision 10-14's rules:

- **A cloned device.** A library folder restored on a second device, or an older copy restored on the same one, gets its own device ID (SY7).
- **A clock ahead.** Minutes ahead: named in Settings › Sync, and a concurrent place may go to the device that is ahead (SY10). More than a day: set aside, never applied silently.
- **Compaction during the week.** A thing deleted, then compacted away from the change files, can still be restored with all it had (SY11, SY17, SY19).
- **Two full libraries meeting.** No duplicate books or highlights (SY8, SY29).
- **A newer format.** Records from a newer Linen are kept and passed on, never rewritten or dropped (SY9).
- **Ping-pong.** The same book open on two devices (SY12).
- **Reading backwards on purpose.** The newest place wins (SY12).
- **Undo.** Undo after a delete is a newer version, so the thing comes back everywhere (SY19).
- **A conflict about a conflict.** Two devices settle the same conflict differently while apart: shown again (SY13).
- **A different edition on each device.** Unplaceable highlights go to “Couldn't place”, never dropped (SY16, A8).
- **The storage misbehaving.** Placeholders, half-synced files, conflict copies, the folder moved, the storage full or signed out (SY11, SY25, SY30).
- **A storage that lost files.** Never a deletion (SY21).
- **A device away for months.** Tombstones last (SY17, SY20).
- **Per-book keys.** `simplifyStyles:<bookId>` and `book_settings` name local IDs and are translated (SY8).
- **Safe mode, and a provider turned off.** Nothing syncs; Settings › Sync says why; nothing is lost (SY5).
- **A provider stuck or suspended (P6).** Sync pauses, with Restart in Settings › Sync, as other slots show.

## 8. Risks

1. **Losing the reader's books, notes or place** is P0. Mitigations: missing is never deleted (SY21); tombstones only; a book file is never purged before it is in storage, and expiry waits for every enrolled device's own measure of the week (SY17); a consistent backup of the database and the books before every pass that replaces or removes a book (SY27); large removals wait (SY26); the soak test (Stage 1).
2. **The folders behave differently across macOS versions** (iCloud Drive and Google Drive both use File Provider, which changes). Stage 0 measures them; SY30 keeps every storage problem quiet and harmless.
3. **The iPad (#80).** iPadOS reaches these folders only through the document picker and security-scoped bookmarks. Decision 10-14 says no iCloud container is needed; whether a folder kept open that way can be written in the background, and whether Google Drive's Files provider allows it, is unchecked. It must be checked when #80 is planned, before Stage 6.
4. **Size.** Books can be large and iCloud's free tier is 5 GB. The setup sheet says the size (SY6); a full storage only stops books (SY25).
5. **A device that missed a removal.** Someone who controls the folder and holds a removed device's key can hide the removal from a device that hasn't synced since, and that device then still accepts the removed device's signed changes. Nothing inside the folder can prove freshness to it; only another channel could. Mitigations: SY26's guards and SY27's backups bound the damage, the Remove flow tells the reader to open Linen on their other devices, and the protocol document (Stage 1a, #86) settles whether a device that has seen no other enrolled device's fresh frontier for some days stops applying deletions.
6. **A slow storage blocks saving.** The prototype held the store's lock while reading the folder; SY32 forbids it.
